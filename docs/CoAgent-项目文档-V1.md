# CoAgent 项目文档 V1

**版本：** V1 — 市场验证版  
**日期：** 2026-07-18  
**状态：** 产品假设，尚未完成用户与付费验证  
**第一读者：** 项目发起人  

> 本文档用于判断 CoAgent 是否值得脱离黑客松继续做，而不是对外宣传。凡未被真实用户、真实事故或付费行为证明的内容，均按“假设”处理。

## 1. 这个产品是什么？

CoAgent 当前建议定义为一个待验证的 **Agent Quality Incident Bridge**：

> 它连接现有的 Agent 观测、评测、事故管理和 CI/CD 工具，把一次 Agent 质量异常转化为有证据、有影响判断、有动作边界、有责任人、有恢复标准和有回归用例的处置闭环。

它不再试图成为新的 Trace Store、通用 Eval 平台或自动修复 Agent。

预期工作流：

```text
在线 Eval / 用户反馈 / Trace 异常
    → 聚合为质量事故
    → 证据与反证
    → 影响和严重级别
    → 动作、风险、权限与回滚条件
    → 人工审批或受控执行
    → 前后指标验证
    → 生成或关联 Regression Case
```

针对 FDE 或解决方案商，它还可以生成可脱敏、可移交的事故证据包，帮助客户、交付方与原开发者在不共享整个后台的情况下协作。

## 2. 它解决了什么问题？

### 已有市场证据支持的问题

Agent 进入生产后，质量和可靠性是主要障碍；团队已经逐渐具备 Trace，但 Eval、治理和持续改进仍不成熟。

- Agent 的错误不是只有 HTTP 失败，还包括错误工具、错误路径、幻觉、策略违规、质量漂移和成本/延迟异常。
- 单次 Trace 能说明“发生了什么”，却不一定回答“是否构成事故、影响多大、谁能做什么、如何证明恢复”。
- 离线 Eval 可以发现回归，却不自动形成线上处置责任、审批和恢复验证。
- Incident Management 擅长召集人和记录时间线，却通常不理解 Agent 的模型、Harness、Prompt、Tool 与 Eval 证据。

### 尚待验证的具体问题

> 在 Agent 质量异常从“被检测”到“被安全解决”的过程中，团队是否存在高频、昂贵、跨角色的手工断层？

尤其需要验证：

- FDE 是否经常在非原作者身份下承担处置责任；
- 团队是否需要在多个控制台、聊天和工单之间拼接证据；
- 决策和恢复验证是否比发现异常本身更痛；
- 用户是否愿意让独立工具接入 Trace、Eval 和 Incident 数据。

## 3. 为什么要做它？

### 市场原因

1. Agent 正从试验进入生产，可靠性、质量和治理需求持续增加。
2. 观测已接近基础设施，Eval 快速普及，市场价值正在从“采集更多数据”上移到“用数据做正确决策”。
3. Agent 的非确定性、工具调用和长程状态，使传统软件测试与 Incident 流程不能原样复用。
4. 中国企业重视私有化、权限、审计和跨组织交付，可能产生与海外 AI-native 团队不同的工作流。

### 项目原因

CoAgent 已经实现事件接入、Playbook、结构化推理、风险分级、人工处置和审计时间线，具备验证这一问题的原型基础。继续验证比从零开始成本低。

### 不能作为理由的内容

- 不能因为黑客松选择过这个题目就继续；
- 不能因为 Agent 市场增长就推断本产品必然有需求；
- 不能因为招聘 JD 重视 Harness/Eval 就反向制造产品；
- 不能用虚拟用户或 Mock 事故证明市场必要性。

## 4. 它有哪些核心创新点？

以下是**待验证的创新假设**，不是已经建立的壁垒。

### 4.1 把 Agent 质量下降作为可处置的事故

不只记录 Trace 或 Eval 分数，而是建立质量事故对象：影响范围、严重程度、责任人、版本、证据、动作和恢复窗口。

### 4.2 将风险评分变成处置合同

评分不能来自模型自报置信度。处置合同应明确：

- 支持与反对当前判断的证据；
- 动作风险与可逆性；
- 谁能执行、谁必须批准；
- 什么条件触发回滚或升级；
- 用什么指标、观察多久才算恢复。

现有三因子把握度评分只可作为原型，必须用真实事故结果重新校准。

### 4.3 连接 Eval 与 Incident，而不是替代两者

上游复用 Langfuse、Phoenix、LangSmith、云平台或 OTel 的 Trace/Eval；下游复用 PagerDuty、飞书、Slack、GitHub 和 CI/CD。CoAgent 只承担跨层决策与闭环状态。

### 4.4 处置结果必须进入回归

事故关闭不等于问题解决。每次处置需要关联一个可以复现或防止同类错误的 Regression Case，并记录改动前后的质量、延迟、成本和恢复能力。

### 4.5 可移交的跨组织证据

为 FDE、客户和原开发者生成脱敏、可审阅、可复现的证据包，减少“只有控制台账号持有者才能解释问题”的依赖。

## 5. 它最大的亮点是什么？

> **不是更快地产生一条 AI 修复建议，而是让团队知道这次 Agent 质量事故该不该动、谁能动、动完如何证明恢复，以及怎样保证它不再发生。**

如果这一价值无法在真实事故访谈和 Concierge Pilot 中被确认，那么它就不是亮点，只是完整但多余的流程设计。

## 6. 当前供需判断

| 市场层 | 需求 | 供给 | CoAgent 判断 |
|---|---|---|---|
| 构建编排 | 高 | 很高 | 不进入 |
| 运行时 | 高 | 快速增加 | 暂不进入底层 Runtime |
| 观测 | 高 | 很高且标准化 | 不重建 |
| 评测 | 高 | 高 | 只做连接与结果消费 |
| 安全治理 | 高 | 巨头进入 | 不做通用安全平台 |
| 可靠性处置 | 中高 | 中高 | 只验证 Agent 质量事故断层 |
| 改进飞轮 | 高 | 快速拥挤 | 不做通用 Failure-to-Eval |

完整证据与竞品地图见 [Agent 工程基础设施市场研究](../artifacts/research/2026-07-18-agent-engineering-infrastructure-cn.html)。

## 7. 当前最大风险

1. 所谓“Quality Incident Bridge”可能只是 LangSmith + PagerDuty + GitHub 的少量集成代码。
2. 真实团队可能更愿意在现有平台内完成闭环，而不采用新控制台。
3. Agent 事故频率可能不足以支撑独立产品。
4. FDE 可能无法取得客户 Trace，或无法统一不同客户的权限和数据格式。
5. 当前 CoAgent 的 Mock 场景过于干净，无法证明对真实长程 Agent 失败有效。
6. 创始人没有生产 Agent 经历，必须通过真实用户和真实失败样本补足认知。

## 8. V1 的验证任务

未来两周不继续扩充功能，完成：

- 12 次真实事故访谈：5 位 Agent/Harness/Eval 团队、4 位 FDE/解决方案商、3 位企业 AI 平台/SRE；
- 获取至少 3 份脱敏 Trace 或事故时间线；
- 人工制作 3 份 Quality Incident Contract；
- 验证用户是否再次使用、是否要求接入现有工具、是否愿意试点或付费。

### 继续条件

- 至少一半受访者近三个月多次遇到类似问题；
- 至少 4 人的处理跨两种以上工具且耗时超过 2 小时；
- 至少 3 个团队愿意提供数据或试点；
- 至少 1 个团队愿意讨论付费或正式开源采用。

未达到条件时，不再以商业产品继续追加功能；可收缩为开源 Agent Failure Evidence / Eval 实验项目。

## 9. 当前一句话结论

> CoAgent 还不是一个被市场证明有必要做的产品；它是一项值得用两周真实用户研究验证的假设：Agent 团队可能不缺发现失败的工具，但仍缺少把质量异常安全地处置、验证并转化为组织记忆的桥梁。
